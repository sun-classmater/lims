h1|一、AI技术基础相关介绍
h2|（一）大语言模型的基本原理
p|大语言模型（LLM）以 Transformer 架构为基础，通过自注意力机制学习词与词之间的长距离依赖关系，在海量文本上预训练后具备语言理解与生成能力。模型以 token 为处理单位，受上下文窗口限制；经过指令微调与对齐后，能够按照自然语言指令完成问答、写作、代码生成等任务。
h2|（二）从“对话模型”到“智能体”
p|单纯的对话模型只能输出文本，不能读取文件、执行命令或查询数据库。智能体（Agent）可以理解为“模型 + 工具 + 循环 + 记忆”：模型负责理解与决策，工具负责与外部世界交互，循环让它“思考—行动—观察”直到任务完成，记忆则通过上下文、项目规范和历史记录维持一致性。工具调用（Function Calling）与 ReAct 是其中两种典型实现方式。
h2|（三）提示词与规范文件
p|提示词决定模型的行为边界。本次实训把项目约束固化在 AGENTS.md 中，包括技术栈、目录结构、分层职责、数据库规范、安全红线和构建门禁，相当于给智能体一份长期生效的“项目说明书”，每次会话都会自动加载，显著降低了输出偏离的风险。
h2|（四）本次实训中的 AI 能力边界
p|我们用到的能力包括：理解自然语言与截图需求、阅读并重构代码、执行命令行、查询数据库、生成测试与文档。同时也认识到它的局限：可能产生幻觉、上下文长度有限、对运行环境的真实状态依赖工具探测，涉及业务语义的映射必须由人确认。
h1|二、如何搭建AI智能体（步骤）
h2|（一）准备运行环境
p|安装 Codex 客户端并接入模型；准备 JDK 17、Maven 3.9、Node.js、MySQL 8 等工具链；确认本地 Maven 仓库与 npm 依赖可用。由于网络受限，依赖能否离线获取会直接影响方案选择。
h2|（二）建立项目工作区与规范
p|把前后端代码放在同一工作区，在根目录编写 AGENTS.md，明确 Vue3 + Spring Boot 3 的技术栈、controller/service/mapper 的分层职责、表结构与审计字段规范、权限必须由后端校验等要求。规范越具体，智能体的产出越稳定。
h2|（三）配置工具与权限
p|为智能体开放文件读写、命令执行等工具，并按沙箱规则控制可写范围；涉及启动服务、访问数据库、修改数据等操作时逐次确认授权。把可复用的流程沉淀为技能（SKILL.md），需要时再加载，避免污染上下文。
h2|（四）建立“取数—修改—验证”闭环
p|先让智能体阅读代码和数据库结构，再动手修改；每次修改后运行 mvn compile、npm run build、vue-tsc、ESLint，并用真实数据调用接口回归。验证不通过就回到上一步，形成闭环。
h2|（五）联调与交付
p|启动后端（8081）与前端（5173），浏览器打开页面，用测试账号登录并检查关键链路；确认前端代理、JWT 鉴权、数据库连接均正常后，再交付使用。
h1|三、如何使用AI智能体
h2|（一）需求输入
p|以“参考图片完成某页面”的方式给出明确目标，并补充数据口径、字段来源和交互预期。把大需求拆成可验证的小步骤，一次推进一个闭环：确认数据模型→编写后端接口→实现前端页面→构建与实测。
h2|（二）典型工作流
p|以 LIMS 为例：先检索路由与页面，定位可复用组件；再查询数据库确认字段含义与状态位；随后新增 Service/Controller（统一响应、参数校验、事务）；前端补充 API 封装与页面，复用编号弹窗、文件下载等公共组件；最后跑构建与真实数据验证。
h2|（三）提高产出质量的做法
p|要求智能体先说明假设再动手；对无法确认的业务映射显式标注；把重复逻辑抽成公共组件；要求给出可核对的证据（构建结果、接口返回、数据条数）；对删改数据的操作先备份、后执行、再还原。
h1|四、遇到的问题及解决方法
h2|（一）中文乱码
p|PowerShell 默认按 ANSI 读取 UTF-8 源码，控制台会出现乱码。解决方法是读取文件时显式指定 -Encoding utf8，接口返回按 UTF-8 字节解码核对，确认乱码只发生在终端显示而不是数据本身。
h2|（二）旧库业务语义不清
p|state_div、state_arrange、state_verify 等状态位没有文档，部分备注列全部为空。解决方法是按状态分组统计并结合样例数据反推口径，同时在代码注释和汇报中明确写出假设，避免“看起来对”。
h2|（三）基础数据缺失
p|标准库 sa001 在 lib 表中没有记录，抽样任务表只有 4 条数据。解决方法是页面给出明确提示而不是静默失败，并把数据缺口作为待办反馈给使用者。
h2|（四）依赖受限
p|生成 Excel 需要 poi-ooxml，但本地 Maven 仓库没有且网络受限。解决方法是改用已有的 POI HSSF 生成 .xls，既满足功能又不新增依赖。
h2|（五）跨页面不一致
p|同一类弹窗在多个页面各写一份，容易出现行为差异。解决办法是抽成全局组件与共享状态，让所有页面调用同一份实现。
h2|（六）测试会污染数据
p|接口实测会写入数据库。做法是先记录原始值，测试后逐项还原，并核对总行数与状态分布，确保数据回到测试前。
h1|五、主要心得体会
p|通过这次实训，我认识到 AI 更像是“结对编程”的加速器，而不是替代者。智能体可以快速完成页面搭建、接口编写和问题定位，但业务语义、验收标准和风险判断仍需要人来把关。
p|规范先行事半功倍。把技术栈、分层职责、数据库约束写进 AGENTS.md 之后，智能体的输出明显更可预期，返工更少。验证闭环比“看起来对”更重要，类型检查、构建、ESLint 和真实数据回归缺一不可；只有跑通并核对过数据，才能说功能完成。
p|还要保持可逆。凡是涉及数据修改的测试，都先记录、后执行、再还原，这样既验证了功能，也不破坏原有数据。最后是拆解能力的提升：把“做一个页面”拆成“摸数据—写接口—做页面—验证”四步，每一步都有明确产出，AI 才能稳定推进，人也更容易发现问题。整个实训下来，我完整走了一遍 LIMS 从登记、分解、安排、检验、签发到报告与导出的业务流程，对全栈协作和数据一致性有了更具体的理解。
